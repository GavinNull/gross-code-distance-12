### 1.3 篡改、截断与错配

E-034 的 14 种必须拒绝的篡改我没有逐个重做（它们是 E-031 审计那 8 种加上 E-031 自己的 6 种，记录在 `validation/tamper_v3.jsonl`，我读过）。我补做的是这次真正新的风险，流式检查下“读到的不是完整的那份证明”（`trunc.py`，`results/E-034-audit/trunc.jsonl`，Z W7 的已通过证明经管道喂给 VeriPB 3）：

| 变体 | VeriPB 3 | 打印 `s VERIFIED UNSATISFIABLE` |
|---|---|---|
| 原样 | rc 0 | 是 |
| 截在 10%（行中）、50%、99%（行边界）、`output` 行前、`conclusion` 行前、`conclusion` 行中间 | rc 1，语法错误（EOF） | 否 |
| 去掉最后的 `rup >= 1`（结论指向不存在的编号） | rc 1 | 否 |
| 空流、只有版本行 | rc 1 | 否 |
| 同一证明配另一实例的 .opb（Z W8 + 585） | rc 1（`f 290` 与 875 条约束不符） | 否 |
| 截在 `end pseudo-Boolean proof;` 行前 | **rc 1，但先打印了 `s VERIFIED UNSATISFIABLE`**，再报缺 `end` | 是 |
| 只少最后一个换行 | rc 0 | 是 |

倒数第二行值得记下：VeriPB 3 在读到 `conclusion UNSAT : id;` 并核对了 id 是矛盾之后就打印判定，之后才发现缺少 `end`。这不是可靠性问题（矛盾已经推导并核对过，后面只缺一个结束标记），但它说明“只看输出行、不看退出码”的判据会把这种截断流算作通过。E-034 所有被接受的记录 rc 都是 0（runs.jsonl 逐条看过），所以对结论没有影响；发布包若加入 VeriPB 检查，判据应是 `s VERIFIED UNSATISFIABLE` **且** rc = 0（`conclusion NONE` 时 rc 也是 0，所以两者缺一不可）。

能不能让 VeriPB 对一份“与生成器输出不一致”的流给出 UNSAT？不能以有害的方式：VeriPB 检查的是它读到的字节，任何被它接受的流本身就是该 .opb 的一份 UNSAT 证明，与它是不是 pbdfs 原样写出的无关。所以“截断或错配的流”只有两种结局：被拒，或者本身仍是一份正确的证明。流 sha256 的作用是让别人能重生成并核对 VeriPB 读到的正是这份证明（3.2、3.3 我就是这样核对的），不是可靠性的前提。真正必须核对的是 VeriPB 读到的 .opb：五个 u11 .opb 的 sha256 与记录相同，我用 `build.py` 重新生成也相同，语义检查见 3.1。

## 2. `-F N` 清理规则

### 2.1 可靠性：不依赖钉住规则

论证分两层。

第一层（与 `-F` 无关）：证明在第 223 行之后只有 `pol`、`rup`、`del`、最后的 `output NONE` / `conclusion UNSAT`。`pol` 和 `rup` 是蕴含规则，导出的约束是当时数据库的逻辑推论；数据库在对称步骤之后始终是“F ∧ 对称子句”的推论集合的子集。`del` 只会让数据库变小，变小不可能让一条原本推不出的 `rup` 变得推得出，也不可能让 `pol` 引用一个不存在的约束（VeriPB 会报错，见下）。会因为删除而变“容易”的只有 `red`/`dom` 一类的强化规则（检查目标来自当前核心），而所有 `red` 都在第一条 `del` 之前（我对 `-F 1`、`-F 50` 的证明逐行确认过）。被删的全是 `pol` 导出的奇偶子句（导出约束集合中的约束，`strengthening_to_core on` 下删导出约束不需要检查），从不删输入约束或对称约束。所以无论清理删了什么、删得对不对，VeriPB 接受的 UNSAT 都是真的。

第二层（VeriPB 的行为，实测）：被删的约束如果之后又被引用，VeriPB 3 直接拒绝，报 `Trying to access constraint with ID … that has already been deleted.`。我做了一个变异版 pbdfs（`pbdfs_mutant.c`，只把两处 `pin_push` 用环境变量关掉）：

| 变异 | 实例 | 结果 |
|---|---|---|
| 不钉住分支帧的 `base` 奇偶子句，`-F 1` | [[90]] Z W7 | 第 623 行被拒（ID 793 已删） |
| 不钉住叶子返回的非自有证书，`-F 1` | [[90]] Z W7 | 第 677 行被拒（ID 847 已删） |
| 同上，`-F 50` | [[90]] Z W7 | 第 1 480 行被拒（ID 1 602 已删）；我的 `proofscan.py` 独立扫出 2 621 处引用已删编号，第一处正是第 1 480 行的 1 602 |
| 同上，`-F 100` | [[90]] X W8 + 585 | 第 4 379 行被拒（ID 5 148 已删） |

两类钉住缺了任何一类都会被拒，而且拒绝来自 VeriPB，不是来自生成器。所以“错误的清理只会让验证失败，不会让它错误地通过”这一点我实测确认了。

### 2.2 钉住规则为什么够（证明能通过的原因）

读代码（`e034/pbdfs.c` 第 123–144、186–229、231–347 行），缓存里的条目只有 `row_clause` 导出的奇偶子句；`cache_trim` 只在 `node()` 入口执行，只删缓存条目。一个缓存条目在被导出之后、被最后一次引用之前，若中间经过了 `node()` 入口，就必须被钉住。逐个看引用点：

- 分支帧的 `base`：在进入第一个子节点之前导出并立刻 `pin_push`，在本帧的 `rup` 写完之后 `npin = pin0` 弹出。钉住。
- 子节点返回的证书：`owned = 1` 的（新 `rup`、`pol`）不是缓存条目，清理碰不到；`owned = 0` 的（叶子直接返回的奇偶子句、阻断子句编号）在返回后立刻 `pin_push`，到本帧 `rup` 之后弹出。钉住。
- 剪枝与紧界的 `pol`：`rid[]` 导出后紧接着写 `pol`，中间没有 `node()`。不需要钉。
- 紧界证书 `xcert`（祖先 `rup` 都会引用，经 `xstack`）：是 `pol` 的结果，不是缓存条目，只由本帧在 `rup` 之后删除。
- 每个 case 顶层：`node()` 返回后立刻写 `rup ~x_col`。最后：`cache_flush` 之后重新导出 q 行的奇偶子句，再写无提示的 `rup >= 1`。
- 栈纪律：钉住列表按帧压入、按帧弹出（`pin0`）；子帧的钉在子帧返回时已弹出，父帧随后压入子帧返回的编号。重复编号无害。`id < 0`（找到解或节点上限）时同样恢复 `npin`。
- 缓存键是 (行, T)，导出式还依赖当前已全局否定的列（`gfalse`）；`gfalse` 只在 case 之间变化，每个 case 开头 `cache_flush`，与 E-031 相同。清理后再次需要的子句会以新编号重新导出，`lcache`（默认 `leafrup = 1` 时不用）按编号匹配，找不到就新做一个 `pol`，不会引用旧编号。

所以本帧和所有祖先帧里还没写出的 `rup` 所要引用的缓存编号，恰好就是被钉住的那些。

## 5. 论文措辞

我的判断：**现在可以说“两个定理证明中用到的每一个不可行性断言都附有检查过的证书”**，前提是同时保留 E-031 审计要求的限定语。

逐项对照：

- gross 周期 11 电路（u11）：d_ext ≥ 10（E-031，VeriPB，两基底，E-031 审计 CONFIRMED）；权重 10、11 列表完备（本实验，VeriPB 3，两基底，本审计 CONFIRMED）；lift R = 1..31（E-031，drat-trim + cake_lpr，CONFIRMED）。E-031 审计 3b 里唯一的缺口（144 / 7344 完备性无证书）已经补上。
- [[90]] c11：d_ext ≥ 8 与 585 / 16830 列表完备（E-031，VeriPB，用 c16 的扩展码；c11 用同一组列这一点由 Table I 断言，我在 c11 R25 上独立核对过）；lift R = 1..25 两基底，每批都经 drat-trim 与 cake_lpr（本审计 CONFIRMED）。E-031 审计 3c 的缺口（R = 20–25）已补上。

仍然必须写明、不能删的限定：

1. 编码（扩展码、OPB、lift CNF、DEM）由我们的代码从电路生成；它们等于目标问题，靠的是独立实现的比对（逐字节 / 语义 / 实例级），不是证书。
2. Lemma 1 / Table I 与任意 R 的约化（R'_9 = 25、R' ≤ 12、R' = 31）是数学论证，其前提（分离、周期性）是计算核对。
3. W11 两个证书各只被 VeriPB 3 检查过一次（检查需要约 18 GB 内存）；VeriPB 3 是这些 PB 证明唯一的检查器（W ≤ 9 的较小证明另经 VeriPB 2 检查过）。这一条不必进正文，但 SM 里应当给出复现所需内存。

建议正文（u11）可以用 E-034 的句子，只改一处：把 “proofs of up to $4.6\times10^{11}$ bytes, checked as streams” 保留，并加上流哈希的用途，例如：

> “For the period-11 gross circuit, $d_{\rm ext}=10$ and the completeness of the lists of 144 weight-10 and 7344 weight-11 extended logicals (both bases) are certified by pseudo-Boolean proofs checked with VeriPB~3; the largest proofs ($4.6\times10^{11}$ bytes) were generated deterministically and checked as streams, and we record the SHA-256 of each stream so that it can be regenerated and compared. The encodings were generated from the circuits by our code and cross-checked against independent implementations; the reduction to these finite problems is a mathematical argument whose premises were verified computationally.”

仍然不能写 “all computational inputs are certified” 或 “fully formally verified”。

## 6. 发现的问题（交给 lead）

1. **VeriPB 判据宜加 rc = 0。** 截在 `end pseudo-Boolean proof;` 之前的流会让 VeriPB 3 先打印 `s VERIFIED UNSATISFIABLE` 再以 rc 1 退出（1.3）。不影响可靠性，也不影响 E-034 的任何结论（所有被接受记录 rc = 0），但 `certify3.py` 写着“退出码只记录不使用”，发布包若加 VeriPB 脚本应要求输出行与 rc = 0 同时成立。
2. **W11 的复现需要约 18 GB 内存**（编号索引表，与 `-F` 无关）。24 GB 机器能跑但要单独跑；SM 或复现说明应写出来。Z 侧 W11 那次是在严重换页下跑完的，结论不受影响（VeriPB 结论只取决于读到的字节）。
3. `run_u11.sh` 被运行中改写导致的 `cert11_*.out` 末尾语法错误，日志已如实写明，记录在 runs.jsonl 之后发生，不影响结果。
4. 小事：我的 X W11 种植（#1378）在 4×10^8 节点内未决；若想要两侧各两个独立种植，可把上限放到全树大小（约 2.2×10^9，约 7 CPU h）。
